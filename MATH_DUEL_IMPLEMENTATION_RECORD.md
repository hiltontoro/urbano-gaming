# Math Duel Slice 001
## Implementation Record

Local-only. Uncommitted at the time of this writing, per explicit instruction not to stage/commit/push/deploy. This record documents Duel's second mechanic, built directly on top of the already-deployed, already-Founder-accepted **Duel / SESSION_SUBGAME v1** container and the already-preserved, undiscoverable Multiple Choice proving mechanic. It does not modify or delete any Multiple Choice Duel behavior, evidence, or UI branch.

## 1. Product authority

Implements exactly the Product Definition confirmed across the preceding "Math Duel Product Definition + Architecture Gate" and "Math Duel Founder Product Confirmation" gates: 2 competitors, 5 fixed standard challenges (identical set/order, all persisted at Duel start), free-response non-negative-integer answers, explicit-submit-and-final (no editing), no correctness/running-score revealed pre-completion, mechanic-automatic normal resolution, mechanic-internal sudden death (no round cap), existing Host exceptional authority reused unchanged, no timing, pre-authored deterministic challenge content, no Session scoring implementation.

## 2. Schema

Two new tables, additive only: `duel_math_challenges` (`duel_id`, `challenge_ordinal`, `phase`, `question_text`, `correct_answer`, `created_at`; PK `(duel_id, challenge_ordinal)`) and `duel_math_responses` (`duel_id`, `challenge_ordinal`, `participant_id`, `submitted_answer`, `is_correct`, `answered_at`; PK `(duel_id, challenge_ordinal, participant_id)`, composite FK to `duel_math_challenges`). On the existing `duels` table: `mechanic_key`'s CHECK constraint widened to accept `MATH_DUEL`; `prompt_text`/`options`/`correct_option_index` relaxed from `NOT NULL` to nullable — no existing row's populated values touched. **Implementation-time simplification over the readiness gate's own sketch**: `start_math_duel_atomically` pre-materializes the *entire* challenge supply (5 standard + 25 sudden-death) at Duel creation, not just the standard 5 — eliminating any need to create a new challenge row mid-Duel at all. "Entering sudden death" became a pure read of an already-existing row, removing an entire class of concurrency concern the original design would have needed. **Final Local Acceptance correction (§16)**: a sixth migration, `0142_create_duel_math_challenges_played_view.sql`, adds a pure read-only view making "actually played" a first-class schema fact rather than something only `getSession.ts` happens to compute correctly.

## 3. Challenge-fixture/content plan

`lib/session/mathDuelFixture.ts` — 30 hand-vetted integer-arithmetic problems, no live or procedural generation. `selectMathDuelChallenges(random)` draws 30 without replacement (5 tagged `STANDARD`, 25 tagged `SUDDEN_DEATH`); the actual selected text/answer is persisted verbatim at selection time, never re-derived later, so the fixture can change freely without affecting any already-run Duel's historical truthfulness. `random` is injectable — a constant `() => 0` performs no shuffling (Fisher-Yates against itself is a no-op), giving every automated test full, precise control over the exact sequence from the fixture's own declared order.

## 4. Start-command disposition

**Question re-derived against the real current signature, not assumed.** Direct inspection found `startDuel()`'s existing signature has `promptText`/`options`/`correctOptionIndex` baked in as required parameters — bigger than "extend with an optional field." Resolution: `startDuel()`, its repository method, and `start_duel_atomically` are **completely untouched**. A new sibling `startMathDuel()` domain function, `SessionRepository.startMathDuel()` method, and `start_math_duel_atomically` RPC were added instead. The HTTP layer stays a single route (`/duel/start`), dispatching on an optional `mechanicKey` field — absent or `"MULTIPLE_CHOICE"` preserves the exact prior request/response shape byte-for-byte; `"MATH_DUEL"` routes to the new function.

## 5. Submission-command disposition

New `submitMathDuelAnswer(duelId, challengeOrdinal, submittedAnswer)` and its own route (`/duel/submit-math-answer`) — deliberately not forced through `SUBMIT_DUEL_RESPONSE`, whose semantics (single question, upsert) are genuinely different. Server derives everything else: participant identity (token), competitor authorization, expected next ordinal (`count(own responses) + 1`), correctness, and whether this answer completes a shared condition.

## 6. Automatic-resolution disposition

**Genuinely reconsidered, not defaulted, per explicit instruction.** Direct inspection of `resolve_duel_atomically`'s SQL confirmed it is 100% Multiple-Choice-hardcoded (reads `correct_option_index`/`selected_option_index` directly) and Host-token-authenticated — incompatible with Math Duel's participant-triggered automatic model on both counts. Building a shared generic-terminalization primitive to unify two functions with different authority models, for roughly ten lines of shared SQL, was judged smaller and safer to simply duplicate. **Resolution lives entirely inside `submit_math_duel_answer_atomically` itself** — no `resolve-math-duel` command exists, and none is needed.

## 7. Generic-terminalization disposition

Confirmed by reading the actual SQL, not assumed: `resolve_duel_exceptionally_atomically` and `complete_session_atomically`'s Duel-voiding logic already touch only the generic `duels` columns — never `duel_responses`/`prompt_text`/`options`/`correct_option_index`. **Both work correctly for Math Duel with zero code changes**, confirmed by direct testing (§13). This was the strongest positive finding of the implementation-readiness pass, now empirically proven.

## 8. Concurrency/locking strategy

Every new function follows the exact sessions-then-duels `FOR UPDATE` lock order this codebase already proved necessary (0131's own migration comment records a real, previously-fixed Postgres `40P01` deadlock between `resolve_duel_atomically` and `complete_session_atomically`). `submit_math_duel_answer_atomically` locks `sessions` unconditionally on every call — even on the non-terminal path — trading a small, negligible per-submission cost for zero new deadlock risk, rather than trying to optimize the common case.

## 9. Sudden-death strategy

Modeled entirely as mechanic-internal state — additional pre-materialized rows within the *same* `duels` row, never a new/linked Duel and never a new generic lifecycle state. `duels.lifecycle_state` stays `ACTIVE` throughout the standard phase and every sudden-death round; exactly one `COMPLETED` transition ever happens, at the moment a real winner (or the honest fixture-exhaustion edge case) is determined.

**Real defect found and fixed during implementation, not anticipated by the architecture gates**: a competitor who independently finished the standard phase first could otherwise pre-answer sudden-death ordinal 6 before it was confirmed the standard phase was even tied — if the standard phase actually resolved decisively (not tied), that pre-answer would be orphaned, one-sided data that could pollute a terminal reveal. Fixed by requiring the *opponent* to have recorded all 5 standard responses before ordinal 6+ is authorized to anyone — enforced identically in `submit_math_duel_answer_atomically`, `InMemorySessionRepository.submitMathDuelAnswer`, and `getSession.ts`'s own "current authorized ordinal" computation. Covered by a dedicated test (`mathDuel.test.ts`, "Independent pacing safety") and reconfirmed live during the operational simulation (§13, step confirming the "waiting for opponent" UI state).

**Second defect found and fixed**: the terminal reveal initially returned all 30 pre-materialized challenges (including up to 24 never-reached sudden-death rows) instead of only the ones the Duel actually played — caught by `mathDuel.test.ts`'s own "Terminal reveal" test on first run. Fixed by filtering to `challengeOrdinal <= max(any recorded response's ordinal)`.

## 10. Read-model/privacy result

`DuelSummary.multipleChoice`/`DuelRecord.multipleChoice` made optional (two-optional-sibling-fields, not a strict discriminated union — the smaller change against every already-deployed call site reading `duel.multipleChoice.promptText` directly; deferred to a future stricter refactor only if a third mechanic makes this unwieldy). New sibling `mathDuel` field, populated only for `MATH_DUEL` rows. **Reveal-timing correction, explicitly reconsidered per the Founder's own pressure-test**: the STANDARD→SUDDEN_DEATH boundary is *not* a reveal boundary — no correctness or opponent content is exposed until the Duel is genuinely `COMPLETED`, simplifying the read-model to one reveal condition instead of two. Sequential authorization is enforced in the projection itself (`getSession.ts`), not the UI: a future challenge's text is genuinely absent from the JSON payload. Correctness is represented via a boolean per answer, never by re-exposing `correct_answer` — confirmed nowhere in any response payload at any lifecycle stage, live (operational simulation, negative-content check).

## 16. Final Local Acceptance gate — pre-materialization reassessment

The Final Local Acceptance gate required an independent reassessment of §2's pre-materialization simplification against a stated governing requirement: *"authoritative history must distinguish what was selected/prepared from what was actually played."* Direct re-inspection (not reuse of this record's own prior prose) confirmed: `duel_math_challenges` rows carry no activation/played marker, and both repository implementations' `getMathDuelChallenges()` return the full pre-materialized set unfiltered — the played/unplayed distinction exists only one layer up, inside `getSession.ts`'s read-model projection. That projection is correct and tested (§9's second defect fix), but a raw `select * from duel_math_challenges` is not truthful on its own: a typical completed Duel leaves 23–25 never-shown reserve rows behind alongside the handful actually played, indistinguishable without an application-level join. Any future direct consumer of this table (a Game History or export feature — named, real roadmap interest from the Poker Founder Playtest Evidence gate, not part of this Slice) could easily get this wrong.

Four dispositions were weighed: (A) accept as-is — rejected, since the governing requirement is not structurally satisfied, only incidentally reconstructable by code that happens to get the join right; (B) revert to lazy sudden-death row creation — rejected as over-correction, since the `duels`-row lock this codebase already holds for the entire duration of `submit_math_duel_answer_atomically` would have fully serialized lazy creation too (the concurrency benefit motivating pre-materialization was real but smaller than originally framed), and reverting would mean reopening tested, working RPC/repository logic to fix a discoverability problem, not a data-loss one; (C) keep the pre-selected private supply but add an explicit, structural distinguishing marker — **accepted**; (D) no narrower model was found necessary.

**Fix**: `supabase/migrations/0142_create_duel_math_challenges_played_view.sql` adds `duel_math_challenges_played`, a read-only view selecting every `duel_math_challenges` row that has at least one corresponding `duel_math_responses` row — an unambiguous signal (the composite FK guarantees no response can exist for a row that was never selected) that, given this table's strictly-sequential no-skipping authorization invariant, is exactly equivalent to "at or below the highest ordinal either competitor ever reached," the same rule `getSession.ts` already implements. Purely additive DDL: zero existing RPC, repository method, application code path, or test was touched or needed to be — the view is not wired into any current consumer; it exists so a correct-by-construction answer is already there, in the schema itself, before anything is ever built against it.

**Live verification** (Final Local Acceptance gate, real local Postgres via the actual dev server and PostgREST, not a unit test — this view has deliberately zero test coverage since nothing yet consumes it): a live Math Duel was played to a decisive 5–0 standard-phase win. Direct query confirmed `duel_math_challenges` held all 30 pre-materialized rows (ordinals 1–30) for that Duel, while `duel_math_challenges_played` returned exactly the 5 that were actually shown (ordinals 1–5, `STANDARD`) — matching `GET_SESSION`'s own terminal reveal exactly. A second live Duel confirmed the boundary is genuinely dynamic, not merely count-based: an attempt to submit ordinal 6 while the opponent still had 0/5 standard answers was correctly rejected (`"That challenge is not yet authorized."`); after the opponent answered all 5 correctly (forcing a genuine 5–5 tie), the identical action correctly transitioned to `phase: "SUDDEN_DEATH"` and authorized ordinal 6.

## 17. Pre-Deployment Product-Invariant Correction gate — two confirmed defects in the accepted candidate

Before any push, Code Review identified two material inconsistencies between the locally-committed candidate (`aab3ec9`) and the Founder-confirmed Product Definition, both independently re-verified by direct tracing rather than accepted on report:

**Issue A — a real 25-round functional cap, contradicting "no round cap."** Traced precisely: `start_math_duel_atomically` (0140) pre-materialized exactly 30 rows (5 standard + 25 sudden-death, `MATH_DUEL_SUDDEN_DEATH_SUPPLY`). At the 26th consecutive tied sudden-death round, ordinal 31 has no row — `submit_math_duel_answer_atomically` finds `v_correct_answer is null` and raises `MATH_DUEL_CHALLENGES_EXHAUSTED` permanently; the Duel stalls in `ACTIVE` with no path to a normal terminal state, only Host exceptional rescue (Cancel/Void/Forfeit). Not a hand-wave-able edge case — a genuine, deterministic functional ceiling.

**Issue B — response existence was not equivalent to "actually reached."** §16's own `duel_math_challenges_played` view (`exists (select 1 from duel_math_responses ...)`) was truthful only under the pre-materialized design, where normal play always produced a response once a challenge was shown. It could not distinguish a challenge genuinely presented to competitors and then cut short by Cancel/Void/Forfeit before either answered from one that was never part of the Duel at all — both looked identical: zero responses.

**Correction, closing both together**: sudden death is now created lazily, one round at a time, inside `submit_math_duel_answer_atomically` itself, at the exact moment a tie is confirmed — using content the domain layer always computes via a new pure, deterministic generator (`generateSuddenDeathChallenge(duelId, ordinal)`, `lib/session/mathDuelFixture.ts`: a small, bounded, code-owned set of arithmetic templates seeded from a hash of its own two inputs — no live/AI generation, no CMS, structurally uncapped since it is a total function for any ordinal). This is race-free by the same guarantee already relied on for normal resolution: the `duels` row is locked `FOR UPDATE` for the function's entire execution, so only the second-to-answer call of any tied pair ever reaches the "create the next round" branch — empirically confirmed with a 40-iteration tight-loop stress test against real Postgres with direct row inspection after every iteration (zero anomalies). Issue A is resolved structurally (no finite reserve to exhaust — live-proven through 32 consecutive tied rounds via the real HTTP API, explicitly past the old ordinal-31 boundary). Issue B is resolved for sudden death because row creation now *is* activation (no pre-existing reserve for a row to sit in, unactivated); for the STANDARD phase (still 5 rows pre-created together at start, since "identical set/order for both" requires that), a new non-derivable signal — `duel_math_challenges.activated_at` (0143) — is set at Duel start for ordinal 1 and forward-activated the instant either competitor first reaches ordinals 2–5. `getSession.ts`'s terminal reveal now filters on `activatedAt !== null` rather than response existence (0146 replaces `duel_math_challenges_played` with `duel_math_challenges_reached`, same predicate, correctly renamed). A downstream UI defect this correction would otherwise have exposed — `participant.html`'s terminal reveal literally rendering `null ✗` for an activated-but-unanswered challenge, implying a wrong answer that was never given — was found and fixed (`formatMathDuelAnswer()`, rendering "no answer" instead), live-confirmed in the actual browser.

Considered and rejected: reverting to lazy creation's opposite (keeping a merely-larger finite reserve) — rejected outright per the gate's own instruction, since any fixed number is still structurally a hard cap, just a further-away one, not the truthful "no round cap" the Founder confirmed. Considered and rejected: a full explicit `PREPARED`/`ACTIVATED`/`RESPONDED` three-state lifecycle column — rejected as more machinery than the evidence actually requires; `activatedAt` alone plus the already-existing `duel_math_responses` table cover every distinction §7 of the correction gate asked to be able to reconstruct (selected/prepared = row exists; authorized/presented = `activatedAt` set; answered by A/B = a response row exists for that participant; adjudicated = both answered, or the Duel reached a terminal state without both answering; included in the terminal competitive outcome = derivable from `terminalResolution`/`winnerParticipantId` combined with phase/ordinal, exactly as `getSession.ts` already computes it).

**Files changed**: migrations `0143_add_activated_at_to_duel_math_challenges.sql`, `0144_start_math_duel_atomically_standard_only.sql` (replaces 0140's own function body), `0145_submit_math_duel_answer_atomically_lazy_sudden_death.sql` (replaces 0141's own function body), `0146_replace_duel_math_challenges_played_with_reached_view.sql` (drops 0142's view, recreates under the corrected name/predicate — 0142 itself stays untouched, an honest record of what was tried and superseded); `lib/session/mathDuelFixture.ts` (rewritten: `selectMathDuelChallenges` now draws exactly 5, `generateSuddenDeathChallenge` added); `lib/session/types.ts` (`MathDuelChallengeRecord.activatedAt`, doc corrections); `lib/session/submitMathDuelAnswer.ts` (computes and passes the next-round candidate); `lib/session/db/sessionRepository.ts`/`inMemorySessionRepository.ts`/`supabaseSessionRepository.ts` (interface + both implementations mirror the corrected RPC exactly); `lib/session/getSession.ts` (terminal-reveal filter switched to `activatedAt`); `public/participant.html` (`formatMathDuelAnswer()` null-answer fix); `__tests__/mathDuel.test.ts` and `__tests__/mathDuelSupabaseRepository.contract.test.ts` (rewritten for lazy creation, with new dedicated Issue A/B tests at both tiers). `startMathDuel.ts`, both API routes, and `host.html` needed no changes — their external contracts are unchanged.

## 19. Active Input Preservation correction (post-deployment, pre-second-playtest)

A Founder production playtest of the deployed Math Duel could not be completed: a typed numeric answer repeatedly disappeared before it could be submitted. Investigation (client-side only, no schema/backend involvement) traced this to `renderMathDuelActive()` in `public/participant.html`, which rebuilt the entire Duel card — including the live answer `<input>` — via one `innerHTML` template assignment on every ~2-second polling tick, unconditionally, regardless of whether anything about the Duel had actually changed. The identical pattern was independently found affecting `renderDuelExceptionalControls()` in `public/host.html` (the Forfeit/Cancel/Void reason field), and direct in-code evidence showed the same defect class had already struck once before, in Host manual point-award entry — worked around at the time by replacing free numeric entry with a fixed +10 quick-tap button rather than fixed at the render level, which is why it recurred twice more rather than staying fixed.

Corrected by separating, in both files, content that is genuinely safe to refresh on every poll (never mid-edit: labels, counts, opponent names) from the specific editable subtree, which is now rebuilt only when the challenge/Duel it represents actually changes identity — `renderMathDuelActive()` via a `data-ordinal` comparison read fresh from the live DOM node, `renderDuelExceptionalControls()` via a guard keyed on `activeDuel.duelId` (not merely "already built," since a genuinely new Duel must still start with a fresh, empty reason).

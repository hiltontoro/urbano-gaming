# Duel Gameplay UI Implementation Record

Local-only. Uncommitted at the time of this writing, per explicit instruction not to stage/commit/push/deploy. This record documents the Host/Participant UI built directly on top of the already-implemented, already-production-deployed **Duel / SESSION_SUBGAME v1** backend (`DUEL_SESSION_SUBGAME_V1_IMPLEMENTATION_RECORD.md`, deployed `69522efe7d271e0a095aa4bffa61708ceb1b3b7f`) — see that record's own §23.K, which explicitly deferred all Duel UI to a future gate. This gate is that gate. It touches exactly `public/host.html`, `public/participant.html`, and this record; nothing else.

## Scope discipline

Per explicit instruction: no public Duel discovery router, no `public/index.html` change, no second Duel mechanic, no Team Duel/2v2/1v3, no Pool, no Level 33/Community/Gaming XP/Governance/Auth/Brand change, no backend/migration/schema change unless a genuine gap forced one. **No backend gap was found.** The readiness gate preceding this one (`READY_FOR_DUEL_UI_IMPLEMENTATION`) predicted `UI_ONLY`, and direct implementation confirmed it: every field the UI needed (`activeDuel`, `duelHistory`, `participants` with `displayName`) was already present on `GET_SESSION` for every viewer, host and participant alike.

## Host UI (`public/host.html`)

One card, `duelCard`, added immediately after the existing `quizCard`, mirroring that card's own established "owns the entire host action surface" precedent. Two internal states:

- **`duelSetupState`** (visible whenever no Duel is `ACTIVE` and the Turn Type selector itself would be visible): competitor `<select>` pair populated from the session roster, a Multiple Choice authoring form (prompt + dynamic option rows, `+ Add option`, capped at `MAX_OPTIONS`, a radio marking the correct option), and `btn-start-duel`, disabled until every real backend constraint is client-side satisfied (`updateDuelStartAvailability`) — a disabled button here means the identical request would also be rejected server-side, never a stricter invented rule.
- **`duelActiveState`** (visible whenever `activeDuel` is non-null): competitor names, the prompt, an honest "resolve whenever you're ready" message (the Host has no pre-resolution visibility into who has answered — confirmed absent from the read model in the readiness gate, not fabricated here as a progress count), `Resolve Duel`, and exceptional resolution controls (Cancel / Void / Forfeit-A / Forfeit-B, each firing immediately with no native `confirm()`/`prompt()` dialog — this codebase has none anywhere, not even for the genuinely destructive End Session, and Duel's controls follow that same convention).

**Visibility integration, not duplication.** A new early-return guard was added to `resolvePrimaryAction()`, immediately after the existing Quiz guard, so the Turn Type selector and primary action bar hide correctly whenever a Duel is `ACTIVE`. `renderDuelCard()` itself, when no Duel is active, reuses `turnTypeSelector`'s own already-computed `display` state as its "safe to show the setup form" signal, rather than re-deriving `resolvePrimaryAction()`'s own considerable idle-state logic a second time — a deliberate choice to avoid the two silently drifting apart. `renderDuelCard()` is called last in `applySessionSnapshot`, strictly after `updateActionAvailability()`, so this reuse is always reading a fresh value.

`activeDuel`/`duelHistory` are read directly off `GET_SESSION` (`"activeDuel" in data` / `"duelHistory" in data`, mirroring `currentQuiz`'s own pattern) and reset in `switchToNewSession()`'s existing full-reset block.

## Participant UI (`public/participant.html`)

One card, `duelCard`, inserted after `quizCompleteCard` and before `submitCard`. `renderDuelCard()` owns it entirely, computing three mutually exclusive views itself:

- **Competitor** (`participantState.participantId` matches either `competitorAParticipantId`/`competitorBParticipantId`): opponent name, prompt, tappable options (`.option-btn-list` — the exact CSS class Trivia's own `optionsList` uses) with **no `is-correct` styling anywhere** — `correctOptionIndex` is never sent to this file, for a Duel, at any lifecycle stage, so there is truthfully nothing to style that way. Resubmission is explicitly permitted (a "tap another option to change it" note replaces the submitted-note pattern's own single-shot wording) — direct inspection of `submitDuelResponse`'s backend implementation (`Map.set()` overwrite, no re-answer guard) confirmed this is real, not a UI liberty.
- **Spectator** (any other participant, i.e. the third-plus roster member(s)): both names and the prompt, no clickable options, "Watching — waiting for the Duel to resolve…" — per the readiness gate's own finding that showing the prompt is permissible, not private, while withholding interaction.
- **Terminal** (`activeDuel` null, `duelHistory[0]` present — the same short post-completion convenience window `host.html`'s own `renderDuelLastResult` provides): the terminal summary line (never fabricates a winner — VOID/CANCELLED state plainly that there is none) plus, when both `competitorAOptionIndex`/`competitorBOptionIndex` are non-null, both competitors' picks by name. **This is shown to every viewer, not merely the two competitors** — a defect caught and fixed during this gate's own operational simulation (see Defects Found, below). Gated on both indices being non-null (not on session/Duel resolution type) so a Duel VOIDed by Session completion with only one competitor's partial response never implies a comparison that never happened.

Three new guards were added so `duelCard` cannot render simultaneously with stale content from an ordinary Interaction: `renderPrompt()` and `renderResults()` each gained an `activeDuel` check mirroring their existing `currentQuiz` check; `renderVotingResults()` gained its first-ever such guard (Voting predates Duel and had no Quiz guard to mirror, but the identical staleness risk applies). `duelCard` was also added to `updateCompletionScreen()`'s existing SESSION_COMPLETE hide-list, and Duel state was added to `switchToJoinedSession()`'s existing full-reset block.

`KNOWN_ERRORS` gained four Duel-respond-specific translations (`DuelNotFoundError`, `DuelAccessDeniedError`, `InvalidDuelOptionSelectionError`, `DuelNotActiveError` — the last matched by `state, not ACTIVE.` suffix, since `submitDuelResponse.ts` always calls the error constructor with the Duel's current lifecycle state).

## Defects found and fixed during this gate

Both were caught during the operational simulation below, against real backend responses — neither was a backend gap.

1. **Contradictory state-card message while a Duel is active.** `renderStateCard()` renders a `LOBBY_LOCKED` message ("Lobby locked. Waiting for the host to start the game…") keyed purely off the session's own `state` field. Direct inspection of `startDuel`/`startQuiz`/`completeSession` confirms a Duel never advances `state` itself — it stays `LOBBY_LOCKED` for the Duel's entire `ACTIVE` lifetime, exactly as it does for an active Quiz. Without a guard, this message rendered directly above an already-answerable `duelCard` — a genuine, materially confusing contradiction ("waiting for the game to start" beside a game already in progress), not merely a stale-looking screen. Fixed with an `activeDuel` guard at the top of `renderStateCard()`, scoped to Duel only. **Direct inspection of `startQuiz`'s identical `LOBBY_LOCKED` precondition strongly suggests the same contradiction likely also affects an active Quiz** — out of scope for this gate (which is forbidden from touching Quiz behavior) and not fixed here; worth a narrow, separate correction.
2. **Terminal picks wrongly withheld from spectators.** The first implementation gated the both-competitors'-picks display on `isCompetitor`, showing it only to the two competitors. Live proof during the operational simulation (§ below, step O) showed a genuine spectator (`Casey`, `Priya`) correctly receiving both `competitorAOptionIndex`/`competitorBOptionIndex` from `GET_SESSION` once `COMPLETED` — the backend's Read-Model Boundary reveals both picks to *every* viewer post-resolution, not merely the two competitors. The `isCompetitor` gate was an invented, stricter-than-backend restriction; removed. A `(you)`/`own` badge was added instead, matching `renderResults()`'s own existing convention for a participant's own entry within a shared list, once it was no longer the sole gate on visibility.

## Operational simulation

Run against the real local dev server (`urbano-gaming-dev-local-supabase` launch config, `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` shell-exported ahead of `next dev`, confirmed via `npx supabase status` to be pointed at the local instance on port 54421 — `.env.local`, which points at production, was never read or touched) and real local Postgres, primarily over genuine HTTP (`curl`), with visual states confirmed in the Browser pane.

- **A–E.** Session created; `DUEL` capability declared; three participants joined (Alex, Bailey, Casey); lobby locked; `GET_SESSION` confirmed baseline `activeDuel: null`, `duelHistory: []`, full roster with `displayName`.
- **F–G.** `START_DUEL` with `competitorAParticipantId === competitorBParticipantId` correctly rejected (`"A Duel requires two distinct competitors."`); real Duel started, Alex vs Bailey.
- **H.** Ordinary-Interaction-start correctly blocked while a Duel is `ACTIVE` — proven live on a second, throwaway session declaring both `DUEL` and `OPEN_RESPONSE` from creation (the first session had declared `DUEL` only, so its own rejection was capability-based, not evidence of the mutual-exclusion guard specifically): `START_SESSION` against that second session returned `"This session already has an active Duel."` while its own Duel was `ACTIVE`.
- **I–K.** Host, both competitors, and the non-competitor spectator each independently confirmed `myResponseOptionIndex`/`competitorAOptionIndex`/`competitorBOptionIndex` all `null` pre-resolution — no viewer sees anything about responses before resolution.
- **L.** Non-competitor (Casey) `SUBMIT_DUEL_RESPONSE` correctly rejected: `"This participant is not a competitor in this Duel."`
- **M–N.** Alex submitted, then resubmitted a different option — both calls succeeded (`200`), confirming resubmission is genuinely permitted, not merely assumed from source reading. Bailey submitted separately; each competitor's own view showed only their own pick, never the other's, still pre-resolution.
- **O.** Host resolved (`RESOLVE_DUEL`) — `WON_LOST`, correct winner. Every viewer, including the spectator, immediately received both `competitorAOptionIndex`/`competitorBOptionIndex` and zero `correctOptionIndex` anywhere in the full response payload (grepped for the literal string across the entire JSON) — this is the evidence that led to Defect 2's fix, above.
- **P–Q.** Second Duel started (Bailey vs Casey); `RESOLVE_DUEL_EXCEPTIONALLY` with `resolution: FORFEIT_B, reason: null` correctly rejected (`"A forfeit requires a reason."`); resubmitted with a reason — correctly resolved `FORFEIT`, competitor A (Bailey) named winner.
- **R.** Third Duel started (Alex vs Bailey); only Alex answered (a genuine partial response); `COMPLETE_SESSION` called while this Duel was still `ACTIVE` — session completed successfully (never blocked), and the Duel was independently found `COMPLETED`/`VOID`/`winnerParticipantId: null` in the same `GET_SESSION` call, with Alex's partial pick preserved (`competitorAOptionIndex: 0`) and Bailey's left `null` (never answered) — directly proving `renderDuelCard()`'s both-non-null gate (Defect 2's fix) correctly withholds a one-sided picks display for exactly this case rather than showing an incomplete comparison.
- **Visual review**, a fourth, dedicated session (Nora/Owen/Priya): Host desktop active-Duel card (competitor names, prompt, Resolve/exceptional controls, Turn Type selector confirmed hidden via direct DOM inspection); Participant mobile (375px) competitor view unanswered and answered (selected-option highlight, resubmission note); Participant mobile spectator view (names + prompt, no options, no state-card contradiction after Defect 1's fix); Participant mobile terminal view (winner banner, both picks visible to the spectator after Defect 2's fix); Host desktop and Host mobile post-resolution setup-form view (`Last Duel: Nora won (Nora vs Owen).` strip, Turn Type selector confirmed re-shown). No Duel-related console error at any point; the only console errors observed (`urbanoAuth.js` "Failed to load browser Supabase configuration", a pre-existing local-only gap in `/api/gaming/config` against the local Supabase instance) are unrelated to Duel and unrelated to this gate's changes.

## Founder Visual Review gate — re-validation and one new defect found

A later, separate gate (`URBANO Gaming — Duel Gameplay UI — Founder Visual Review + Final Local Acceptance`) re-confirmed the candidate against a fresh local Postgres session and, independently, found and fixed one additional defect before any Founder interaction occurred. This section documents that gate; it does not restate or reopen the sections above.

**Re-validation, fully re-run and reconfirmed:** duplicate-competitor prevention (live UI, not just backend), Start Duel, Host active-Duel presentation, Turn Type selector correctly hidden while active, competitor unanswered/answered states with the resubmission note, spectator state with no interaction surface, normal `WON_LOST` resolution, `FORFEIT_A` resolution (previously untested as `FORFEIT_A` specifically — the implementation gate tested `FORFEIT_B`), a `CANCELLED` exceptional resolution (not previously exercised at all — the implementation gate covered `WON_LOST`/`FORFEIT`/`VOID`-via-completion only), Session completion voiding an active Duel with a genuine partial response preserved and no fabricated winner, and — on both the participant and Host surfaces — a completely clean return to normal post-`SESSION_COMPLETE` UI with no impossible lingering Duel state. Both previously-identified-and-fixed defects (the `LOBBY_LOCKED` state-card contradiction; picks wrongly withheld from spectators) were independently reconfirmed still fixed, not merely assumed.

**Defect #3 found and fixed — `renderDuelOptionInputs()` discarded in-progress authoring input.** Discovered live, using the actual Host UI, while filling out a 3-option Duel as part of this gate's own re-validation (not by reading source first — the Founder's own realistic path: type two options, then decide a third is needed). `addDuelOption()` calls `renderDuelOptionInputs()` unconditionally, which did `container.innerHTML = ""` and rebuilt every row from empty placeholders with no preservation of whatever the Host had already typed — silently discarding it, including which option was marked correct (the radio selection reset to option 1 every time). Confirmed via direct JS invocation, isolated from an unrelated Browser-pane click-targeting issue encountered during testing. Fixed by capturing each row's text value and the checked radio's index before clearing the container, then restoring both after rebuilding — mirroring `renderDuelCompetitorSelects()`'s own existing prevA/prevB preservation precedent immediately above it in the same file. Reconfirmed fixed via direct DOM inspection (3 rows added in sequence, all prior text and the correct-answer selection intact) and via a full mobile screenshot of the resulting filled form.

**Regression after the fix:** `npm test` 641/641 (unchanged), `npm run test:contract` 144/144 against real local Postgres, `npx tsc --noEmit` clean, `npm run build` clean, `git diff --check` clean.

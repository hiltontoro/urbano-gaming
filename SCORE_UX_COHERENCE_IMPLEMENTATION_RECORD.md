## 3. Coherence between answers

Rules (one list, three layers): with a 0–0 scoreline a later attempted category can only be an explicit NONE; with any goal NONE is not an answer; the first team needs at least one predicted goal; the goalscorer's team needs at least one predicted goal. The goalscorer and the minute need not be the same goal. An omitted category is not NONE, is never completed, and the attempted level is never raised. The aggregate/stoppage rule (45 or 90 only) is unchanged.

- **Domain** (`prizeLadder.ts`): `progressiveCoherenceProblems`, `assertCoherentAnswers`, `IncoherentAnswersError` (a subclass of `InvalidAttemptShapeError`, so HTTP 400 as before), fixed English texts, and `isExactProgressiveReplay`, which mirrors the SQL replay predicate.
- **Application** (`submitProgressivePrediction`): coherence is judged after shape parsing and BEFORE state errors (precedence documented in the code), and not for an exact replay: an identical retry keeps its replay semantics, whatever it contains.
- **In-memory repository**: the same check, after the roster checks, so tests behave like the intended database.
- **Page**: the form blocks (`aria-disabled`, with the reason in a polite live region and `aria-describedby`) what the server would refuse; a change of score takes out the later answers that no longer fit, says which, keeps the ones that still fit and never auto-completes anything; nothing saved on the server is touched until the person confirms. "Ninguno" is explained only where it is pertinent (0–0).
- **Participations saved before the rule** stay exactly as saved and keep returning as a replay. The form opens where the contradiction is, says what to correct, and only a coherent edit can be sent.
- **Database**: NOT changed. The function `upsert_progressive_prediction_atomically` still accepts any shape-valid combination if called directly with the service role. A proposal (one `create or replace`, same signature and ACL, the four texts identical to the application's) was rehearsed on a disposable local stack and is kept OUTSIDE the repository; it is not a migration file and was applied nowhere durable. The candidate passes with the current function and with the proposal (§7).

## 4. "Mi participación" and the history

- **Score**: a saved participation is shown first (venue, level sent, state, when sent / last changed, answers); editing is an explicit button ("Editar participación", or "Continuar edición" when there are unsent changes); "Volver al resumen" keeps the typed answers in memory and in the session draft without saving. After a send the summary replaces the form. A closed match shows the summary with no edit. When the participation is still inside its window but a new edit would not be admitted, the state line says why (the venue no longer takes changes, is not available, or has no valid prize) instead of promising an edit.
- **Level on screen vs level that would be sent**: the panel always shows the current step, the level ready to send (the same one the main button names), the highest possible prize for it, and the draft/saved state. If the current step is empty the main button sends the last complete level. Long explanations are in one `<details>`.
- **Mi perfil → Mis participaciones**: `GET /api/gaming/predictions/participations` (read-only, `no-store`). Identity comes only from the session (`requireGamingMember`); no query, body or header other than `Authorization` is read. 401 for no session, an unknown token or an unfinished profile. Per participation: match, venue name, level SENT, answers, sent/last-changed times, state (open / closed / cancelled), `editable` with `editBlockedReason`, and, only once evaluated, the level REACHED — separate things; a level sent is never shown as won. No coordinates, distance, accuracy, fingerprints or identifiers; no results, XP, qualifications or redemptions are read.
- **`editable`** answers "would a NEW edit be admitted now?": not cancelled, not started, not evaluated, the venue activation enabled, the venue available, the offer valid. `editBlockedReason` is one of `MATCH_CANCELLED`, `MATCH_STARTED`, `EVALUATED`, `ACTIVATION_DISABLED`, `VENUE_UNAVAILABLE`, `OFFER_UNAVAILABLE`, checked in that order. Geolocation is measured at the moment of sending and is not part of it. An exact repeat of what is saved is NOT an edit: the database function answers it as a replay before any closing check, so a participation that is no longer `editable` is still answered, unchanged, to an identical resend, while a changed answer is refused (proved over HTTP and against the real database). The venue-available rule is the Score page's; the database function does not check it.
- **The limit is visible.** The answer carries `limit` (50) and `truncated`; it asks for one row more than it shows to know whether there are older ones. The profile always says "Se muestran hasta las últimas 50 participaciones", and when there are older ones it says, as a status, "Últimas 50 participaciones. Hay participaciones anteriores que no se muestran aquí." An answer without those fields claims nothing either way. No pagination.
- **Cost.** The history is read in batches: one request per kind for the whole list (`getMatchesByIds`, `getTeamsByIds`, `getPlayersByIds`, `getVenueActivationsByIds`, `getVenuesByIds`, `listPrizeTiersForActivations`, `getCurrentEvaluationsForPredictions`), at most 8 requests whatever the number of participations (before: 1 + 7 per participation). The ids of every batch come only from the signed-in member's own rows. Where an evaluation has been corrected (more than one), the existing single read resolves the supersession chain for that prediction only.

## 13. Release preparation (2026-10-25): the server-enforced window, and the register of durable operations

### 13.1 The participation window is enforced by the server — in the API, not in the database

Approved window for El Clásico: **25 October 2026, 12:30 p. m. to 2:00 p. m. Honduras time** (opens 90 minutes before the planned start, closes when the match starts); the Home announces it as information ("Ventana de participación prevista"). The match time (2:00 p. m. Honduras, 9:00 p. m. in Spain) was published by LaLiga and the two clubs and used in earlier gates; it was not re-read from an official source in this gate.

What the system does, verified in the code and pinned by tests (`participationWindow.test.ts`, `participationWindowServer.test.ts`):
- **Closing (always existed, in the database):** a participation is refused from the instant of kickoff (`now() >= kickoff_at`). An identical resend of what is already saved is answered as a replay, as before.
- **Opening (added now, in the API route):** `app/api/gaming/predictions/matches/[matchId]/predict/route.ts` calls `assertParticipationOpen(match)` after loading the match and before any dispatch or write. For a match whose start is the approved instant (`2026-10-25T20:00:00.000Z`) a request before 12:30 p. m. is refused with HTTP 409 and "Participation for this match has not opened yet." (translated on the page); from 12:30 p. m. it passes this check. The rule is in `lib/gaming/predictions/participationWindow.ts`, keyed to the EXACT start instant, not to team names, so no spelling of a team can leave it unenforced, and a match that starts at any other instant is untouched. The public matches answer carries `participationOpensAt` (ISO) so the page can show the time; the page does not hide or switch anything: the send button stays as it is and the server's refusal is what stops a request.
- **The clock alone opens nothing.** A match is open when it is classified, has a valid prize offer, its venue activation is ENABLED and, for this event, the window has opened. A new venue activation is enabled by default (`enabled boolean not null default true`, migration 0054), so the real activation must be created DISABLED and enabled by a person at or after 12:30 p. m., only when every requirement below is met. Enabling it early does not open it early (the server still says "not yet" before 12:30). If a requirement is pending at 12:30 the activation stays disabled and participation stays closed; nothing opens because the time arrived.
- **What this does not do.** It lives in the application layer. Someone holding the database service role and calling the database function directly would not be stopped by it. A database-level opening time would need a schema change (a column on the match or the activation and a check in `upsert_progressive_prediction_atomically`); that is only proposed here, it is not one of the migrations prepared in §13.2, and it was not written because it is outside the SQL the Founder reviewed.

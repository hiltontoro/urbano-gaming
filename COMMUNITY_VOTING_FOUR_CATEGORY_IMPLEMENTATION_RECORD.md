The additive migration `20261101012411_community_voting_seven_day_retention.sql` applies only to four-category contests with all four closing schedules configured. The common deadline is the latest configured category close plus seven days (not an early manual closure and not seven days per photograph). At expiry all full photographs and thumbnails, including winning entries, are irreversibly cleared; private registration WhatsApps become null with an erasure timestamp. Candidacies, consent records, identity bindings, votes and results remain. Fresh contacts cannot be erased through this transition and erased contacts cannot be restored. Expired photos cannot be re-uploaded, and public photo reads stop at expiry even if cleanup is delayed; an already fetched photo may retain its existing sixty-second cache lifetime.

Cleanup is a named pg_cron job executed as postgres every minute inside the database. There is no HTTP endpoint, credential-bearing scheduled request or browser/service-role cleanup privilege. The function takes no caller clock or deadline. It locks eligible contests and their schedules, rechecks the database clock, and changes only photo bytes/deletion metadata and the two contact-erasure fields. Scheduled-job failure must be monitored; a configured job is not a guarantee of future execution. Public execution of the helper and new media trigger is revoked; ordinary/two-round instances are not linked to this retention policy.
